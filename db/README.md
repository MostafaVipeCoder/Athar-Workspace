# db/ - Stage 1 (LOCAL) database migration

Target: the local Docker Postgres only (container `supabase_db_stack`, database `postgres`). `run.sh` refuses any container
whose name does not start with `supabase_db_`. No remote project is ever touched. No business data is loaded here (stage 2).

## Layout and order
| File | Purpose |
|---|---|
| `migrations/m00_preflight.sql` | schemas (`legacy`, `migration`, `app_private`), extensions, `migration.*` bookkeeping tables, baseline capture |
| `m01_freeze_and_isolate_legacy.sql` | moves the 48 old tables, 2 enums, 14 functions to schema `legacy`; drops old auth trigger; closes `legacy` to API roles |
| `m02` / `m03` / `m04` / `m05` | target schema: identity+structure+graph / entities+forms+lists / modules (booking, certificates, ...) + `google_connections` / `app_private` worker tables |
| `m06a` .. `m06d` | helper + trigger functions (revision bump, tombstone, `handle_new_user`, `merge_companies`) and the RPCs of design 04 section 5 |
| `m07_rls_grants_storage_policies.sql` | RLS policies, grants (anon revoked), storage buckets and policies, realtime publication (`node_revisions` only) |
| `verify/v01..v03` | legacy isolation / structure + security census / RLS role-switch tests (test rows live in transactions that are rolled back) |
| `MIGRATION-LOG.md` | what was executed, results, deviations, open items |

All migrations are idempotent (`if not exists`, `create or replace`, explicit-list moves), so re-running on the same DB is safe.

## Run
```
bash db/run.sh                 # m00..m07 then v01..v03 on the local postgres DB (log in local-db/logs/)
bash db/run.sh migrations      # only migrations      | bash db/run.sh verify   # only verifications
bash db/run.sh file db/migrations/m03_schema_entities_forms_lists.sql
DB_NAME=stage1_test bash db/run.sh     # against another DB inside the container
```
## Re-run from a clean state (proof)
```
bash db/test-from-scratch.sh   # restores the baseline dump into scratch DB stage1_test, runs m00..m07 + v01..v03 (the STAGE-1 gates), drops it
```
(`v02` SEC.5 is a range check and `v03` CE01b / CE01c are stage-aware, so these files pass on a database that only has stage 1 AND on the fully built one; the strict later-stage equality of the anonymous function list is `v10`'s.)
## Baseline / restore
`local-db/backups/baseline-pre-migration.dump` (pg_dump custom format, 2215366 bytes, sha256
`0474c41573a9236eb83d894e9442b96d7a738293e7620c7ae014b61e37ff17f5`) is the pre-migration copy. To return to it, restore into a
fresh database (do not restore over the live auth/storage schemas):
```
docker cp local-db/backups/baseline-pre-migration.dump supabase_db_stack:/tmp/baseline.dump
docker exec supabase_db_stack psql -U postgres -c "create database restore_test"
docker exec supabase_db_stack pg_restore -U postgres -d restore_test --no-owner /tmp/baseline.dump
```
(32 harmless `ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin` errors are expected because `postgres` is not that role.)

# Stage 2a - business data load (LOCAL)  (files m10..m90, v10..v13)

Loads the business data from schema `legacy` (48 old tables, never modified or deleted) into the new `public` schema. Local Docker Postgres only
(`run2a.sh` refuses any container that is not `supabase_db_*`). No Storage object is moved/downloaded (stage 2b), no secret is copied, no remote project is touched.
Checkpoint taken before the load: `local-db/backups/pre-stage2a.dump` (git-ignored; sha256 `a212fb8e9376c53868ddcebd56f15ab1f285624597d06718627f473ff6f67a12`, 2949793 bytes).

Every file is ONE transaction that ends with checks; a failing check raises and rolls the whole phase back. All inserts are `ON CONFLICT DO NOTHING` / guarded, so a re-run on a loaded DB changes nothing.

## Run
```
bash db/run2a.sh                 # m10..m90, then v10 and v11   (needs stage 1 = m00..m07 applied, see above)
bash db/run2a.sh load            # only the loaders            | bash db/run2a.sh verify   # v01 + v10 + v11
bash db/run2a.sh file db/migrations/m12_load_entities.sql
bash db/reconcile.sh             # regenerate db/RECONCILIATION.md
DB_NAME=stage2a_test bash db/run2a.sh      # against another database inside the container
```
(`db/run.sh` now only runs the stage-1 files `m0*` / `v0*`; v02/v03 stay valid for the clean-slate stage-1 state and are replaced by v10/v11 on loaded data.)

## Prove from-scratch + idempotency + rollback
```
bash db/test-stage2a-from-scratch.sh   # restores pre-stage2a.dump into scratch DB stage2a_test, runs m10..m90 + v10/v11, runs the loaders a 2nd time,
                                       # diffs a 1464-line fingerprint (real DB == scratch run 1 == scratch run 2), drops the scratch DB
```
Rollback = restore `local-db/backups/pre-stage2a.dump` into a fresh database (same procedure as the baseline above, file name changed). Inside a phase, rollback is automatic (one transaction).
There is deliberately no in-place "undo" script: stage 2a only ADDS rows to `public` / `app_private` / `migration`; `legacy`, `auth` and `storage` are only read.

## Replacing the fake Google by the REAL credentials (later)
1. The owner does steps 1-5 of `docs/design/10-google-integration-setup.md` (Cloud project inside the organization, APIs, Internal consent screen, scopes, Web OAuth client with the redirect URI above) and keeps the client ID / secret out of chat and out of git.
2. **First disconnect every connection made against the fake** (Profile > Google account > Disconnect, super_admin: the system sender too): their tokens are fake and only the fake Google knows them.
3. Edit `local-db/functions.env`: put the real values into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, and **delete the five fake lines** (`ALLOW_FAKE_GOOGLE`, `GOOGLE_AUTH_BASE`, `GOOGLE_TOKEN_URL`, `GOOGLE_REVOKE_URL`, `GOOGLE_API_BASE`). Keep the generated `OAUTH_STATE_SECRET`; `APP_URL` must be the dev server's address.
4. `bash db/scripts/dev-functions.sh restart`. The fake is no longer started, `status` says "REAL Google", and `up` REFUSES to start while `GOOGLE_CLIENT_ID` is empty or still the `fake-...` placeholder (so a half-edited file can never send placeholder values to the real Google). Leftover `GOOGLE_*` address lines make the functions refuse every call with `not_configured` (the code refuses overrides without `ALLOW_FAKE_GOOGLE=1`), and `status` names them.
5. Click through the checklist of step 9 of the design 10 document with a throwaway PM whose e-mail is a real `@athareg.com` mailbox. `verify-edge-functions.mjs` refuses to run in real mode (it must only ever talk to the fake).
6. Production is a separate step (design 10 section 10): secrets on the live project, a NEW `OAUTH_STATE_SECRET`, `--no-verify-jwt` only for `google-oauth-callback`, `email-worker` and `image-convert`, the schedulers of the e-mail worker and the calendar sync, no `ALLOW_FAKE_GOOGLE`.

## Troubleshooting
* **Ports.** Used here: 54321 (Kong = API + `/functions/v1`), 54322 (db), 54323 (studio), 54399 (fake Google; change with `FAKE_GOOGLE_PORT` AND the four addresses in `functions.env`), 8083 (edge inspector, only when asked), 5174 (`npm run dev:local`). Windows reserves ranges for itself: `netsh interface ipv4 show excludedportrange protocol=tcp` (on this machine 5433-5632 and 50000-50059 are excluded, so a dev server on 5603 fails with `EACCES`; 5702 and 5174 work). `EACCES` = reserved range, `EADDRINUSE` = another program: `Get-NetTCPConnection -LocalPort <n>` shows who. The script stops with a clear message when 54399 answers like a fake it did not start.
* **Docker memory / disk.** The whole stack with the edge runtime needs about 1 GB of RAM (`docker stats --no-stream`: edge runtime ~100 MB, realtime / studio ~190 MB each, db ~100 MB) and the edge-runtime image is 1.1 GB on disk. Docker Desktop on this machine shows 7.7 GB. A container that restarts or shows `Exited (137)` was OOM-killed: close other containers, raise the WSL2 limit (`%UserProfile%/.wslconfig`: `memory=6GB`, then `wsl --shutdown`), start the stack again. `docker system df` shows what Docker holds.
* **No `/functions/v1` (404 or an empty answer).** (a) The stack was started with `-x edge-runtime`: `cd local-db/stack && npx supabase stop && npx supabase start -x logflare,vector,imgproxy,mailpit`. (b) The functions are down (`dev-functions.sh status`, then `up`): after `supabase stop` / start, a reboot or `down`, the serve process is gone and Kong has no upstream. A stale pid file is harmless (`up` ignores it, it never kills a stranger).
* **Two copies of `functions serve`.** `npx -> node -> supabase.exe` is a chain of processes; after a hard stop an orphan can survive and keep the old runtime logic alive. `dev-functions.sh status` flags it ("one copy of functions serve ... N matching processes"); `down` (and every restart) also stops them by command line, so `down` then `up` always cleans up. A healthy start shows exactly 2 matching processes (npx's node and `supabase.exe`).
* **Function logs.** `dev-functions.sh logs functions -n 100` (add `-f` to follow) or `docker logs supabase_edge_runtime_stack`. Lines like `[Error] {"event":"google_oauth_connected",...}` are NORMAL: the functions log structured events through `console.error` (no token, code, state or secret is ever in them: keys that look secret are redacted). `Error: Missing authorization header` is the gateway refusing a request without a JWT (expected for the unauthenticated probes). `google_config_error` + `missing=NAMES` = a required name is absent from `functions.env`. `serving the request with supabase/functions/<name>` shows which function ran. A `?google=error&reason=server_error` redirect means "look at this log".
* **"Connecting Google is not set up on this server yet" (HTTP 503 `not_configured`).** A required name is missing or `OAUTH_STATE_SECRET` is shorter than 32 characters (`status` lists both), or fake lines are left in real mode. After editing the env file run `dev-functions.sh up` (it restarts the runtime when the file changed; `status` flags a file changed after the start).
* **The fake Google is not reachable from the functions** (`status`: "reachable from containers" fails, the token step fails with a network error). The container resolves `host.docker.internal` to the host; Docker Desktop forwards it to a loopback-bound server, so the default `127.0.0.1` works here. If it does not (an older Docker): `FAKE_GOOGLE_HOST=0.0.0.0 bash db/scripts/dev-functions.sh restart` (Windows Firewall asks once: allow PRIVATE networks only; the fake has no authentication on its control endpoints, so never expose it).
* **The first start is slow or fails with a download error.** The runtime fetches `npm:@supabase/supabase-js@2` on the first request and caches it in the Docker volume `supabase_edge_runtime_stack` (needs internet once; a proxy that blocks `registry.npmjs.org` breaks it). `status` times out after 4 minutes with the log tail.
* **A change to the code does not show.** The stack serves its OWN COPY: edit `supabase-new/functions/...`, then `bash db/scripts/sync-functions.sh` (never edit `local-db/stack/supabase/functions/`, the next sync overwrites it).
* **Back from Google to the wrong page or port.** `APP_URL` in the env file is not the dev server's address: `dev-functions.sh up --app-url http://127.0.0.1:<port>`. A `redirect_uri_mismatch` from the fake means `GOOGLE_REDIRECT_URI` changed after the fake started: `restart` (the fake takes the URI, client id and secret from the same file).
* **CORS.** Locally Kong's CORS plugin answers the preflight and sets `Access-Control-Allow-Origin: *` itself; the function's own origin allow-list (`ALLOWED_ORIGINS`, default = the origin of `APP_URL`) is exercised by the unit tests and applies on the hosted project.
* **Windows / Git Bash.** Run the scripts from Git Bash (`bash db/scripts/...`). If you kill a process by hand use `MSYS_NO_PATHCONV=1 taskkill /PID <winpid> /T /F` (Git Bash rewrites `/PID` into a path otherwise). `supabase stop` keeps the data volumes (`supabase_db_stack`, `supabase_storage_stack`); never use `stop --no-backup`. The CLI prints "a new version is available": harmless (installed 2.84.10 works).
* **Going back to the old setup** (no edge runtime): `dev-functions.sh down; cd local-db/stack && npx supabase stop && npx supabase start -x logflare,vector,imgproxy,edge-runtime,mailpit`. The data survives either way; the checkpoint before this change is `local-db/backups/pre-edge-runtime.dump` (restore recipe: "Baseline / restore" above).

## Alumni quarterly figures: known limits (m66 - m70)
- Frozen snapshots are protected by the RPC code only (no guard trigger): the owner / service role can UPDATE or DELETE them directly, `alumni_merge_company_data` drops the dropped company's snapshot of a quarter the kept company also has, and `company_snapshots` cascades on a company delete. `alumni_freeze_due` takes one advisory lock per company for the whole run (fine to a few thousand companies).
- A closed company WITHOUT `closed_on` counts as closed in every quarter frozen after it was marked (the date is unknown): set the date.
- Logs: Postgres logs the statement of a failing call. Keep `log_min_error_statement` at `error` or higher only where the arguments carry no personal data; in production set it to `panic` for the API roles or `log_statement = none`. The test inputs that appeared in the local log were synthetic.
- Closed-company follow-up (m70): the answer is per COMPANY (any founder of it, or the manager, writes it; the latest wins and the quarter's reminders stop for every founder of that company). The quarter status page counts figures reminders per FOUNDER (m68 design), so a closed company of a founder who also has an active one shows that founder's figures reminder. Re-run m70 after any re-run of m68 / m69.

## Athar Network experts registry: decisions and known limits (m75 - m77)
- **Run order**: m75, m76, m77, m78 (each re-runnable; m78 replaces some functions of m76 / m77, so run it again after any re-run of them). m75 re-derives `search_text` / `name_key` / `name_skels` for every expert on each run, so a change of `expert_norm` / `expert_skeleton` is picked up by re-running it. After m75 the `network_experts` columns of the 44 migrated records are byte-identical (checksum of the original columns unchanged); only the new derived columns were added.
- **Access (assumed, not decided by the owner)**: every staff role reads and creates / edits / archives / imports; only the super_admin merges, soft-deletes, restores, dismisses a duplicate pair, renames / archives a tag. Since m78 the RPCs are the ONLY writer of `network_experts` (no INSERT / UPDATE privilege for authenticated; the Lists node already created through `create_network_expert`); `deleted_at` / `merged_into` / `kind` are super_admin-only in the guard trigger too, and the CHECKs refuse a malformed URL / link / photo path / e-mail whoever writes. Founders and anon: no access; nothing of the registry is public.
- **Participation is live, never stored**: `app_private.expert_participation`. Totals are global for every staff role; per-engagement rows only for projects the caller manages (`is_project_manager`); the rest of the engagements are returned as a count only. A session = a confirmed booking through the expert's booking provider, or a mentoring-distribution session WITH a company; withdrawn items are shown flagged to a PM who may see the project and are not counted.
- **Merge**: one transaction, no data loss (the duplicate is soft-deleted with `merged_into`, its full before-image and the plan are kept in `app_private.network_expert_merges`); `purge_soft_deleted` (m06) may hard-delete the soft-deleted duplicate after 90 days, the audit row keeps the data. It is NOT undoable from the screen. If a new table starts pointing at a list item the merge refuses with `unhandled_reference:<table>` instead of leaving a dangling reference.
- **Duplicates**: a candidate generator (trigram similarity of normalised names, a consonant skeleton across Latin / Arabic, the same LinkedIn / e-mail), >= 0.95 is blocking for create unless forced. On the migrated data it finds exactly the 3 real pairs; none was merged. Since m78 the candidates come from stored keys and the pairs of the whole registry are kept in `app_private.network_expert_pairs` (a trigger recomputes a record's pairs on create / name / e-mail / link / kind / delete changes; two writers that add look-alikes at once are serialised by an advisory lock). After a change of `expert_norm` / `expert_skeleton` / `expert_match` run m75 (re-derives the keys) and then `select app_private.rebuild_expert_pairs();` (m78 does it once).
- **Photos**: `global/expert-photo/<uuid>.webp` + `_t.webp`; staff (not only the super_admin) may add / replace / remove them (policies `public_assets_insert_expert_photo` / `public_assets_delete_expert_photo`); the central WebP rules of m41 still apply. A replaced photo's old path is returned by `update_network_expert` ONLY when no other record (live, soft-deleted, merge before-image) still points at the file, the client removes it, and the storage delete policy refuses a file that is still in use; the folder pattern is the same in `expert_clean`, a table CHECK and both storage policies; the storage insert policy accepts `image/webp` only.
- **Intentional deltas of the data fingerprint (v13)**: +2 public tables (`expert_tags` 18 rows, `network_expert_tags` 0 rows), +2 `app_private` tables (`network_expert_merges`, `network_expert_nondup`, both empty), +16 public functions (the RPCs above) and +15 `app_private` functions (helpers, triggers, `expert_participation`), +2 public policies (staff SELECT on the tag tables), +2 storage policies, new columns / indexes / triggers on `network_experts` and `list_items`. No row of any pre-existing table changed.
- **Participation of hidden items (decided in m78; the owner can change it)**: a legacy HIDDEN list item (`list_items.excluded`, the 2 migrated provider items: a booking provider of a legacy event that is not shown in the public list) counts when it has a real role (provider / mentor / presenter) or sessions, and is flagged "hidden" on the profile; a hidden item that is only "listed" does not count. The migration's catch-all program "Legacy projects" (3 old events: OD-4 of docs/design/05) counts as a program until the owner assigns its projects to real programs; the registry follows automatically (everything is derived live). Scheduled sessions count regardless of date, so "last participation" can be a future date; sessions without a recorded date show "Date not recorded".
- **Known limits**: tag management has no screen yet (RPC `update_expert_tag` exists); the import creates experts only (never team members, never overwrites); search is a `like` over a derived text (fine for thousands of experts, not a full-text engine).
